# Pony++ 语言开发——总体方案与系统架构设计文档

## 一、项目背景与愿景

### 1.1 背景

当前并发编程领域存在三个难以兼得的方向：

| 语言/系统 | 优势 | 短板 |
|-----------|------|------|
| Pony | 引用能力（Reference Capabilities）在编译时消除数据竞争；每Actor独立GC，无全局STW；Actor模型天然适配并发 | 不原生支持WebAssembly；生态较小 |
| Erlang/OTP | 监督树提供工业级容错；百万级轻量进程；热代码升级 | 运行时较重；性能不如系统级语言 |
| WebAssembly | 通用沙箱；跨平台；组件模型解决模块间互操作 | 缺乏原生Actor模型支持；GC支持尚在完善中 |

Pony++的愿景是：融合Pony的类型安全 + Erlang的容错体系 + WebAssembly的通用沙箱，打造一个"天生云原生"的新一代编程语言。

### 1.2 核心设计目标

| 目标 | 说明 |
|------|------|
| 编译时数据竞争自由 | 继承Pony的引用能力系统，在编译期保证无数据竞争 |
| Actor模型作为一等公民 | 每个Actor是独立的Wasm模块或组件，拥有自己的堆、栈和消息队列 |
| Erlang风格监督树 | 内置Supervisor机制，实现"Let it crash"容错哲学 |
| 原生Wasm沙箱 | 编译产物为Wasm组件，运行在任何支持WASI的宿主上 |
| M:N调度 | M个Actor映射到N个系统线程，工作窃取调度器 |
| 热代码升级 | 借鉴Erlang，支持不停机更新Actor行为 |

## 三、核心模块详细设计

### 3.1 语言层：引用能力系统

Pony++完整继承Pony的六种引用能力：

| 能力 | 含义 | 并发保证 |
|------|------|----------|
| iso | 唯一可变引用 | 全局唯一，无其他引用可读/写 |
| trn | 写唯一引用 | 唯一可写，同Actor内可读 |
| ref | 本地可变引用 | 仅同Actor内可读写 |
| val | 全局不可变 | 永远不可变 |
| box | 本地只读 | 同Actor内可读 |
| tag | 仅标识 | 仅可发送消息，不可读状态 |

Pony++新增：Wasm-aware的跨组件引用能力——当Actor跨Wasm组件边界通信时，编译器自动插入序列化/反序列化逻辑，确保引用能力在组件边界依然有效。

### 3.2 语言层：Actor模型

每个Actor是独立的计算单元：

```pony
// Pony++ 伪代码示例
actor Counter
  var count: U64 = 0
  
  be increment() =>
    count = count + 1
  
  be get(): U64 =>
    count  // 同一Actor内顺序执行，无锁[reference:24]
```

Wasm原生映射：每个Actor编译为一个Wasm组件实例，拥有独立的线性内存。Actor间消息传递通过Wasm组件模型的接口调用实现。

### 3.3 语言层：监督树（Supervision Tree）

借鉴Erlang/OTP的监督树设计：

```
┌─────────────────────────────────────────────────────────────┐
│                     根监督者 (Root Supervisor)              │
│  ┌───────────────────────────────────────────────────────┐  │
│  │  策略: one_for_one / one_for_all / rest_for_one     │  │
│  └───────────────────────────────────────────────────────┘  │
│                          │                                   │
│         ┌────────────────┼────────────────┐                 │
│         ▼                ▼                ▼                 │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐        │
│  │  监督者 A   │  │  工作者 B   │  │  监督者 C   │        │
│  │  (策略: ...)│  │  (Actor)    │  │  (策略: ...)│        │
│  └─────────────┘  └─────────────┘  └─────────────┘        │
│         │                │                │                 │
│         ▼                ▼                ▼                 │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐        │
│  │  工作者 A1  │  │  工作者 B1  │  │  工作者 C1  │        │
│  └─────────────┘  └─────────────┘  └─────────────┘        │
└─────────────────────────────────────────────────────────────┘
```

核心机制：

· 监督者监控子进程（工作者或其他监督者）
· 子进程崩溃时，监督者根据策略重启
· 在Wasm中，崩溃的Actor实例被销毁并重新创建

### 3.4 运行时层：调度器

设计原则：M:N调度——M个Actor映射到N个系统线程，工作窃取。

```
┌─────────────────────────────────────────────────────────────────┐
│                      调度器架构                                  │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  ┌────────────┐  ┌────────────┐  ┌────────────┐               │
│  │ 线程 1     │  │ 线程 2     │  │ 线程 N     │               │
│  │ ┌────────┐ │  │ ┌────────┐ │  │ ┌────────┐ │               │
│  │ │Actor A │ │  │ │Actor C │ │  │ │Actor E │ │               │
│  │ │Actor B │ │  │ │Actor D │ │  │ │Actor F │ │               │
│  │ └────────┘ │  │ └────────┘ │  │ └────────┘ │               │
│  │   MPMC队列  │  │   MPMC队列  │  │   MPMC队列  │               │
│  └────────────┘  └────────────┘  └────────────┘               │
│         ↕ 工作窃取 ↕ 工作窃取 ↕ 工作窃取 ↕                     │
│                                                                  │
│  全局就绪队列 (MPMC) ← 新Actor/唤醒的Actor                      │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

Wasm适配：

· 每个系统线程运行一个Wasm实例（或复用实例池）
· Actor切换 = Wasm实例的挂起/恢复
· 参考Lunatic的"gas/reduction counts"实现抢占式调度

### 3.5 运行时层：垃圾回收（GC）

继承Pony的每Actor独立GC，无全局STW：

| 特性 | 实现方式 |
|------|----------|
| 每Actor独立堆 | 每个Wasm组件实例拥有独立线性内存 |
| 无全局STW | GC仅在Actor空闲时触发 |
| 循环引用处理 | ORCA协议 + 环检测器 |
| Wasm GC提案 | 利用Wasm GC提案的原生支持 |

Wasmtime 47已于2026年7月默认启用Wasm GC提案，为Pony++的GC实现提供了坚实的底层支持。

### 3.6 运行时层：监督树管理器

Wasm原生实现的监督树管理器：

```
┌─────────────────────────────────────────────────────────────────┐
│                  监督树管理器 (Supervisor Manager)              │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  ┌────────────────────────────────────────────────────────────┐ │
│  │              监督树描述 (编译时生成)                       │ │
│  │  - 节点类型: Supervisor / Worker                          │ │
│  │  - 重启策略: one_for_one / one_for_all / rest_for_one    │ │
│  │  - 最大重启次数: 3次/5秒                                  │ │
│  └────────────────────────────────────────────────────────────┘ │
│                              │                                   │
│                              ▼                                   │
│  ┌────────────────────────────────────────────────────────────┐ │
│  │              运行时监控器                                   │ │
│  │  - 监听Actor退出/崩溃事件                                  │ │
│  │  - 根据策略决策重启                                        │ │
│  │  - 重新实例化Wasm组件                                      │ │
│  └────────────────────────────────────────────────────────────┘ │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

### 3.7 宿主层：WASI与组件模型

Pony++基于WASI Preview 2构建：

| 组件 | 用途 |
|------|------|
| WIT接口 | 定义Actor间的通信协议 |
| Wasm组件 | 每个Actor编译为一个组件 |
| WASI标准 | 文件系统、网络、时钟等系统接口 |
| Wasmtime | 参考实现，已支持GC和异常处理 |

关键步骤：

4. 监督树分析：识别supervisor和worker声明，生成监督树描述
5. WIT生成：为每个Actor生成WIT接口定义
6. Wasm代码生成：生成Wasm组件（.wasm + .wit）

## 五、关键技术挑战与解决方案

| 挑战 | 影响 | 解决方案 |
|------|------|----------|
| Wasm线程模型 | Actor并发需要多线程支持 | 依赖WASI线程提案；短期内单线程协作式调度 |
| GC与Wasm集成 | 每Actor GC需Wasm内存管理支持 | 利用Wasm GC提案；Wasmtime 47已默认启用 |
| 监督树跨组件 | 监督者需监控跨组件Actor | 利用Wasm组件模型的导入/导出机制 |
| 热代码升级 | 需在不停止服务时更新Actor | 借鉴Erlang的代码替换机制；Wasm组件版本管理 |
| 调试体验 | Wasm调试信息有限 | 启用DWARF支持；生成Source Map |
| 性能开销 | Wasm间接调用开销 | 优化内存布局；利用Wasm的call_indirect缓存 |

## 七、总结

Pony++是一个融合Pony的引用能力安全、Erlang的监督树容错和WebAssembly的通用沙箱的新一代编程语言。其核心架构围绕三层设计：

1. **语言层**：继承Pony的引用能力系统和Actor模型，新增监督树语法
2. **运行时层**：M:N调度器、每Actor GC、监督树管理器——全部运行在Wasm之上
3. **宿主层**：基于WASI Preview 2和Wasm组件模型，实现真正的跨平台沙箱

随着Wasm GC提案在Wasmtime 47中默认启用，以及WASI Preview 3对异步和线程的支持，Pony++的技术可行性正在快速提升。这个项目不仅是一次语言设计实践，更是对"云原生时代编程语言应该是什么样子"这一问题的系统性回答。
