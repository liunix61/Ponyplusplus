## 三、架构设计深度分析

### 3.1 引用能力系统 (评分: 6/10)

**优点：**
- 完整继承 Pony 的六种能力
- 提出了跨 Wasm 组件边界的序列化方案

**问题：**
1. trn 的描述不准确——trn 是"转移引用"，不是"写唯一引用"
2. 缺少 sendable 属性标注（iso/val/tag 可发送，trn/ref/box 不可）
3. 跨组件序列化方案过于简略——未说明序列化格式、零拷贝优化、内存安全保证
4. 缺少类型推导规则——Pony 的类型推导在能力系统中有特殊规则

**建议：**
- 修正 trn 描述
- 增加 sendable 列到能力表
- 增加跨组件数据传递的完整协议设计
- 增加类型推导示例

### 3.2 Actor 模型 (评分: 5/10)

**优点：**
- 清晰的 Actor 隔离概念
- 示例代码简洁

**问题：**
1. `be get(): U64 =>` 示例有误——be 是无返回值的 behavior，有返回值应用 fun
2. 未区分 message sending 和 message passing
3. 缺少 Actor 生命周期（创建、启动、停止、销毁）设计
4. 缺少 Actor 地址/引用模型

**建议：**
- 修正示例代码
- 增加 Actor 生命周期状态机
- 增加 Actor 寻址模型设计
- 增加消息传递语义说明（at-most-once, exactly-once）

### 3.3 监督树 (评分: 6/10)

**优点：**
- 借鉴 Erlang/OTP 的成熟设计
- 三种策略覆盖常见场景

**问题：**
1. 未定义监督树的语言级语法
2. 未设计 Wasm 组件边界的监督传递机制
3. 缺少重启次数/间隔的可配置性
4. 未设计热代码升级与监督树的交互
5. 缺少进程诊断接口（类似 Erlang 的 :proc_lib）

**建议：**
- 增加监督树声明语法
- 增加跨组件监督协议
- 增加诊断接口设计
- 增加热代码升级详细机制

### 3.4 调度器 (评分: 5/10)

**优点：**
- M:N 调度 + 工作窃取是正确选择
- 提到了 gas/reduction counts 抢占式调度

**问题：**
1. 未设计 Wasm 实例与系统线程的映射策略
2. 工作窃取在 Wasm 组件模型中的实现未详细说明
3. 缺少优先级调度、Actor 池化等高级特性
4. 未设计 I/O 线程模型
5. 缺少背压机制（Actor 消息队列溢出时如何降级）

**建议：**
- 增加调度器状态机设计
- 增加 Wasm 实例池设计
- 增加背压和流控机制
- 增加 I/O 线程模型

### 3.5 垃圾回收 (评分: 4/10)

**问题（最严重）：**
1. **Pony 的 ORCA 协议与 Wasm GC 不兼容**——原文档混淆了两者
   - Pony 原生用 ORCA（标记-清除 + 循环引用检测）
   - Wasmtime 47 用 Cheney 半空间复制 GC
   - 两者不可混用，必须明确选择
2. 未设计 Wasm GC 与 per-Actor 堆的关系
3. 未说明内存管理策略（Wasm 线性内存 vs GC 堆）
4. 缺少 GC 暂停时间目标和调优参数

**建议：**
- 明确选择：使用 Wasm GC（Cheney）而非 Pony 的 ORCA
- 设计 Wasm GC 与 Actor 隔离的映射
- 增加内存管理策略详细设计
- 增加 GC 性能目标

### 3.6 宿主层 (评分: 5/10)

**问题：**
1. 未讨论 WASI 0.3 (Preview 3) 的 async 支持
2. 浏览器宿主的线程模型未详细说明
3. 缺少 WASI 接口裁剪策略（哪些 WASI 接口对 Pony++ 必要）
4. 缺少运行时版本兼容性策略

## 四、缺失章节详细分析

### 4.1 标准库设计 🔴 关键缺失

**为什么关键：** 没有标准库，语言只有并发能力但没有 I/O、集合、字符串、数学等基本功能，完全无法实用。

**应包含：**
- 集合类型（List, Set, Map, Queue）
- I/O（文件、网络、标准输入输出）
- 并发原语（Promise, Future, Channel, Mailbox）
- 序列化（JSON, MessagePack）
- 加密和哈希
- 工具类（时间、日期、UUID、Base64）
- 正则表达式
- 数学库

### 4.2 工具链设计 🔴 关键缺失

**编译器 (ponyppc)：**
- 基于 C++ 还是 Rust 还是 Go？
- 前端：词法分析器、语法分析器、类型检查器
- 后端：WIT 生成器、Wasm 代码生成器、链接器
- 优化级别：-O0 到 -O3
- 增量编译支持

**REPL：**
- 交互式开发体验
- Actor 生命周期控制
- 热重载支持

**调试器：**
- DWARF 支持
- Source Map
- Actor 调用栈追踪
- 断点、单步、变量查看

**分析器：**
- 性能分析（火焰图）
- 内存分析
- 并发分析（死锁检测、消息延迟）

### 4.3 测试策略 🟡 重要缺失

**应包含：**
- 单元测试框架
- 属性测试
- 并发测试（数据竞争检测）
- 模糊测试
- 集成测试
- 性能基准测试
- 覆盖率目标

### 4.4 安全模型 🟡 重要缺失

**应包含：**
- Wasm 沙箱隔离模型
- 能力安全（Capability-based security）
- 内存安全保证
- 网络通信安全
- 供应链安全（包管理器安全）
- 安全审计流程

## 五、路线图评估

| 阶段 | 原文档时间 | 评估 | 风险 |
|------|-----------|------|------|
| Phase 0 预研 | 3 个月 | ✅ 合理 | 低风险 |
| Phase 1 MVP 编译器 | 6 个月 | ⚠️ 偏乐观 | 引用能力验证是硬骨头 |
| Phase 2 运行时核心 | 9 个月 | ⚠️ 偏乐观 | GC 集成是最大风险 |
| Phase 3 完整运行时 | 6 个月 | ❌ 不足 | M:N 调度器需要更多时间 |
| Phase 4 生态工具 | 6 个月 | ⚠️ 偏乐观 | 标准库工作量巨大 |
| Phase 5 生产就绪 | 持续 | ✅ 合理 | 持续改进 |

**总评估：** 原文档总计约 30 个月。建议扩展到 40-48 个月（3.5-4 年），并增加更多里程碑验收标准。

**关键风险：**
1. 🔴 Wasm GC 与 Actor 隔离的集成——这是整个方案最大的技术风险
2. 🔴 引用能力验证的编译器实现——Pony 的 libponyc 参考实现复杂度高
3. 🟡 跨组件监督树——需要创新性的 Wasm 组件模型设计
4. 🟡 热代码升级——Wasm 组件不支持运行时代码替换，需要全新设计
5. 🟡 标准库工作量——即使最小可用标准库也需要 6-12 个月

## 七、结论

原文档提出了一个**有野心但可行**的架构方向。核心思路——融合 Pony 的引用能力 + Erlang 的监督树 + WebAssembly 的沙箱——在技术上是成立的，且时机正确（Wasmtime 47 GC、WASI 0.3 async）。

但原文档**深度严重不足**：
- 缺少 7+ 个关键章节
- 关键技术细节模糊（GC 策略、跨组件通信、热升级）
- Pony 引用能力描述有误
- 代码示例不可运行

建议按本报告建议重构文档，预计重构后文档将从当前的 ~5000 字扩展到 ~25000 字，覆盖完整的技术设计。
